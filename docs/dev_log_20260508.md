## 2. 테스트 중 발견된 문제 및 수정 이력

### 2-1. LLM이 누락 파라미터를 되물음

**증상**: "장비 ID 54의 정보 알려줘" → "데이터센터 ID를 알려주세요"

**원인**: system prompt에 기본값 지침 없음.

**수정**: `SYSTEM_PROMPT`에 즉시 도구 호출 규칙 및 기본값 명시.
```
- data_center_id=1 (미지정 시 기본값)
- limit=20
- 시간 범위 미지정 시 최근 24시간
- 절대로 되묻지 말고 즉시 도구 호출
```

### 2-2. LLM이 인사말만 출력하고 도구 미호출

**증상**: "현재 활성 알람 목록 보여줘" → 자기소개 응답 출력

**원인**: gemma 계열 모델이 역할 기반 지시보다 명령형 지시에 반응.

**수정**: system prompt를 `[필수 행동 규칙]` 명령형으로 재작성. 인사/소개 금지 명시.

### 2-3. tool 호출 로그 미출력

**수정**: `ainvoke` → `astream_events(version="v2")`로 교체.

출력 형태:
```
[TOOL CALL] get_active_alarms
  input: {'data_center_id': 1, 'limit': 20}
[TOOL RESULT] get_active_alarms
  output: [{'alarm_id': 101, ...}]
에이전트: 현재 활성 알람은 ...
```

### 2-4. 빈 결과 시 `(응답 없음)` 출력

**원인**: `on_chat_model_end`가 도구 호출 단계(AIMessage with tool_calls)와 최종 답변 단계 모두 발생. tool_calls가 있는 응답을 `final_content`로 캡처.

**수정**: `tool_calls`가 없는 응답만 최종 답변으로 캡처.
```python
tool_calls = getattr(msg, "tool_calls", [])
if not tool_calls:
    final_content = msg.content
```

### 2-5. "3층 장비 보여줘" → `floor_id=3` 잘못 파싱

**원인**: `floor_id`와 `location` 파라미터 구분이 docstring에 불명확. LLM이 "3층"을 `floor_id=3`(DB 내부 정수 ID)으로 해석.

**수정**: `search_devices` docstring에 파라미터 선택 기준 예시 추가.
```
- location: 층·구역·방 이름 텍스트 LIKE 검색. 예) '3층', 'A구역', '서버실'
- floor_id: DB 내부 정수 ID (층 번호가 아님). 정확한 값을 알 때만 사용.
- zone_id: DB 내부 정수 ID. 정확한 값을 알 때만 사용.
```

## 3. search_devices tool 신규 구현

### 배경

`get_device_info`는 `device_id` PK 필수 → device_id 모를 때 조회 불가.
기존 `list_devices_by_type`, `list_devices_by_ups`는 단일 exact match만 지원.

### 시그니처

```python
async def search_devices(
    data_center_id: int,
    device_nm: str | None = None,            # LIKE
    device_type_name: str | None = None,     # LIKE
    device_category_name: str | None = None, # LIKE
    location: str | None = None,             # LIKE
    floor_id: int | None = None,             # exact (DB 내부 ID)
    zone_id: int | None = None,              # exact (DB 내부 ID)
    connected_ups: str | None = None,        # LIKE
    manufacturer_name: str | None = None,    # LIKE
    limit: int = 30,                         # 최대 100
) -> list[DeviceSearchResult]
```

- 모든 optional 조건이 None이면 빈 리스트 반환 (전체 조회 방지)
- 조건 1개 이상 시 AND 조합 동적 WHERE 절 구성

### 수정 파일 목록

| 파일 | 변경 내용 |
|------|----------|
| `src/maria_mcp/models.py` | `DeviceSearchResult` 모델 추가 (`DeviceSummary` + `manufacturer_name`, `connected_ups`) |
| `src/maria_mcp/queries.py` | `_DEVICE_SEARCH_COLS` 상수, `build_search_devices_query()` 동적 빌더 추가 |
| `src/maria_mcp/tools.py` | `search_devices()` 구현, 기존 tool docstring 사용 시점 구분 보강 |
| `src/maria_mcp/server.py` | `@mcp.tool search_devices` 등록 |

### tool 사용 시점 구분 (LLM 혼동 방지)

| Tool | 사용 시점 |
|------|----------|
| `list_devices_by_type` | 카테고리/유형 **정확 매칭** |
| `list_devices_by_ups` | UPS 이름 **정확 매칭**, 전원 cascade 분석 |
| `search_devices` | device_id 불명 시, **다중 조건 부분 문자열** 검색 |

## 5. 미해결 / 추후 검토 사항

- `location` LIKE 검색은 인덱스 미적용 → 풀 스캔 가능. 운영 전 DBA와 인덱스 추가 협의 필요.
- gemma 계열 모델의 instruction-following 한계 시 `qwen2.5:14b` 대체 검토.
- `floor_id`, `zone_id` 실제 ID 값 조회 방법 미구현 (사용자가 텍스트로 층을 표현 → `location` LIKE로 우회 중).
