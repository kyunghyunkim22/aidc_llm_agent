# 테스트 검증 가이드

## 0. TDD 개발 순서 (필수)

**구현 전에 테스트를 먼저 작성한다.**

```
1. 테스트 작성 (Red)
   - 구현 없이 테스트 케이스 5개 이상 작성
   - pytest 실행 → 전부 실패 확인

2. 최소 구현 (Green)
   - 테스트를 통과시키는 최소한의 코드만 작성
   - pytest 실행 → 전부 통과 확인

3. 정리 (Refactor)
   - 중복 제거, 가독성 개선
   - pytest 재실행 → 통과 유지 확인
```

**신규 tool 추가 시 순서:**

```
[ ] 1. tests/test_<module>_tools.py 에 TestXxx 클래스 + 5개 케이스 작성
[ ] 2. ! uv run pytest tests/ -k "TestXxx" -v  → 실패(Red) 확인
[ ] 3. tools.py / queries.py / models.py 구현
[ ] 4. ! uv run pytest tests/ -k "TestXxx" -v  → 통과(Green) 확인
[ ] 5. server.py 에 @mcp.tool 등록
[ ] 6. ! uv run pytest tests/ -v               → 전체 회귀 확인
```

## 1. 코드 작성 시 항상 포함할 것

### 구현 함수 + 단위 테스트

신규 함수마다 최소 5개 케이스:

| 유형 | 케이스 예시 |
|------|------------|
| 정상 1 | 기본 입력 → 정상 응답 |
| 정상 2 | 선택 파라미터 포함 → 정상 응답 |
| 엣지 1 | limit 최대 초과 → clamp 적용 확인 |
| 엣지 2 | 빈 결과 → 빈 리스트 / None 반환 |
| 실패 1 | DB 예외 → 예외 전파 확인 |

### 로깅 (Python — `logger.*`)

```python
# console.log 대신 logger 사용
logger.debug("tool=get_device_info device_id=%s", device_id)  # 진입
logger.info("tool=get_device_info elapsed_ms=%d rows=%d", elapsed, count)  # 종료
logger.warning("조건 미충족: %s", reason)                       # 예외 분기
logger.exception("DB 오류")                                     # 예외 발생
```

- `log_tool_call` 컨텍스트 매니저 안에서만 로깅
- `result_count` 는 반드시 `meta["result_count"] = ...` 로 기록

### 가정(assumption) 명시

```python
# [ASSUMPTION] zone_id가 NULL인 장비 입력 시 빈 결과 반환 (에러 아님)
# [ASSUMPTION] device_ids 50개 초과 시 앞 50개만 처리 — 호출자에게 조용히 잘라냄
```

## 3. Mock 원칙

**단위 테스트: DB는 항상 AsyncMock**

```python
@pytest.fixture
def mock_fetch_one(self):
    with patch("src.maria_mcp.db.fetch_one", new_callable=AsyncMock) as m:
        yield m

# 정상 케이스
mock_fetch_one.return_value = {"device_id": 1, ...}

# 빈 결과
mock_fetch_one.return_value = None

# DB 실패
mock_fetch_one.side_effect = RuntimeError("DB connection failed")
```

**통합 테스트: 실 DB만 허용**

- `test_*_integration.py` 파일에서만 실 DB 접속
- 환경변수 `MARIA_HOST` 없으면 자동 skip:
  ```python
  pytestmark = pytest.mark.skipif(
      not os.getenv("MARIA_HOST"), reason="실 DB 환경 없음"
  )
  ```

### clamp 검증

```python
async def test_limit_clamped_to_max(self, mock_fetch_all):
    mock_fetch_all.return_value = []
    await tools.get_active_alarms(data_center_id=1, limit=9999)
    _, _, params = mock_fetch_all.call_args[0]
    assert params[-1] == 15  # limit 최대값 (_LIMIT_MAX)
```

### 파라미터 순서 검증 (IN 쿼리)

```python
async def test_params_structure(self, mock_fetch_all):
    mock_fetch_all.return_value = []
    await tools.get_active_alarms_for_devices(1, [10, 20], limit=5)
    _, _, params = mock_fetch_all.call_args[0]
    assert params[0] == 1       # data_center_id 첫째
    assert params[-1] == 5      # limit 마지막
    assert 10 in params and 20 in params
```

async def test_empty_input_skips_db(self, mock_fetch_all):

## 8. LLM 배치 테스트 (Test A)

LangGraph ReAct 에이전트가 tool을 올바르게 선택·호출하는지 검증하는 end-to-end 테스트.

### 환경 구성

| 항목 | 내용 |
|------|------|
| LLM 서버 | GPU 서버 vLLM (`google/gemma-4-e4b-it`) |
| GPU 서버 접근 | **직접 접속(권장)** — GPU 서버 8000 포트가 공인 IP 로 개방돼 있어 터널 불필요. <br/> 폴백: `ssh -L 8000:localhost:8000 aidc@<gpu-host>` |
| LLM 엔드포인트 | `http://<gpu-host>:8000/v1` (직접) 또는 `http://localhost:8000/v1` (터널 경유) |
| Tool call 파서 | `--tool-call-parser gemma4` (Gemma4 전용, `call:func{args}` 포맷) |
| vLLM 컨텍스트 | `--max-model-len 8192` |
| MCP 서버 | `uv run maria-mcp` (CPU 서버 로컬, 포트 8001) |
| 에이전트 프레임워크 | LangGraph `create_react_agent` + `McpToolClient` |

### GPU 서버 스펙

| 항목 | 내용 |
|------|------|
| GPU | NVIDIA A2 |
| VRAM | 15,356 MiB (약 15GB) |
| Driver | 570.86.10 |
| CUDA | 12.8 |

**max-model-len 결정 근거**

- `max-model-len 8192` + `fp8` + `gpu-memory-utilization 0.90` 기준 VRAM 사용량: **14,726 MiB (96%)**
- 여유 VRAM 약 630 MiB — 값을 늘리면 KV 캐시가 선형 증가하여 OOM 위험
- **8192가 이 GPU/모델 조합의 안정적인 최대값**

### vLLM docker-compose 핵심 플래그

```yaml
command: >
  --model /models/gemma-4-e4b-it
  --dtype bfloat16
  --quantization fp8
  --max-model-len 8192
  --gpu-memory-utilization 0.90
  --enable-auto-tool-choice
  --tool-call-parser gemma4
```

> `--enable-auto-tool-choice`와 `--tool-call-parser gemma4`가 없으면 tool call이 전혀 동작하지 않는다.

### PASS 판정 기준

- `tools_called` 가 1개 이상이고 `error` 가 없으면 PASS
- tool 호출 순서·정확성은 결과 파일의 "예상 결과" 컬럼과 수동 비교

### 에이전트 SYSTEM_PROMPT 규칙

`scripts/run_test_questions.py`에 정의된 7개 행동 규칙:

```
1. 사용자 메시지를 받으면 인사말·자기소개·설명 없이 즉시 도구를 호출하라.
2. 도구 호출 결과를 받은 후에만 텍스트로 답변하라.
3. 파라미터가 불명확할 때 절대 되묻지 말고 아래 기본값으로 즉시 호출하라.
   - data_center_id=1
   - limit=15
   - 시간 범위 미지정 시 start_time=지금으로부터 24시간 전, end_time=지금
4. 사용자가 명시한 장비 타입명·카테고리명은 변환·추론 없이 그대로 파라미터로 전달하라.
   (예: 사용자가 "CRAC"이라 했으면 "CRAH"로 바꾸지 말 것)
5. 다중 조건 질문은 모든 조건을 빠짐없이 파라미터에 포함하라.
6. 특정 장비의 "주변 구역 알람" 또는 "같은 구역 알람"을 조회할 때는 반드시
   get_nearby_alarms(device_id)를 사용하라. 존재하지 않는 tool(예: list_nearby_alarms)을 호출하지 말 것.
7. 검색 결과가 다수(2개 이상)일 때 모든 항목을 반복 분석하지 말고,
   첫 번째 항목 1개만 선택하여 상세 분석하라.
```

> `_LIMIT_MAX=15`는 테스트·운영 공통 적용값이며, 성능 최적화에 따라 변경될 수 있다 (`src/maria_mcp/tools.py`).
> rule 3의 `limit=15`는 이 값과 일치시킨 것이다.
> rule 7은 검색 결과 다수 시 tool을 N회 반복 호출하여 8192 토큰을 초과하는 문제를 막기 위해 추가됐다.

### 알려진 제약

| 현상 | 원인 | 조치 |
|------|------|------|
| 토큰 초과(8192) | 검색 결과 다수 시 반복 tool 호출 | SYSTEM_PROMPT rule 7 (첫 번째 항목만 분석) |
| `list_devices_by_ups` 0건 | DB의 connected_ups 컬럼 데이터 없음 | tool 호출 성공 여부만 검증 |
| his 테이블 이력 0건 (90일) | 최신 데이터 2026-02-05, 90일 초과 | 질문에서 200일로 변경 |

### Gemma4-E4B (W4A16) 모델 한계 — **추가 수정 금지**

아래 항목은 LLM(4B + 4비트 양자화) 자체의 한계로 확인된 케이스. 프롬프트·docstring·MCP 측 보강을 더 시도해도 효과 없음. **동일 이슈 재발 시 코드/프롬프트를 더 수정하지 말 것.** 모델 교체 시점에 재평가.

| 현상 | 시도한 보강 | 결론 |
|------|-------------|------|
| `search_devices` 호출 시 LLM이 존재하지 않는 인자명 `device_location` 사용 | (1) docstring에 "허용 파라미터" 명시 + `'device_location' 없음, 'location' 사용` 문구, (2) SYSTEM_PROMPT에 동일 내용 별도 섹션 추가 | Gemma4-E4B-W4A16 이 무시. 4B 모델 attention 한계로 추정. **더 이상 프롬프트/docstring 보강하지 말 것.** |
| `list_devices_by_type` 호출 시 LLM이 `data_center_id` 인자 누락 | SYSTEM_PROMPT rule 3 에 `data_center_id=1` 기본값 명시. v3 통과 → v4 회귀 | 동일 프롬프트에서도 호출마다 누락 여부가 달라짐 (양자화 모델의 비결정성). **재현성 없는 LLM 변동이므로 수정 추가 금지.** |
| `search_devices` 결과 0건일 때 LLM 이 가짜 device_id (예: 1001, 1005, Cisco/HP 제조사) 생성 | (1) SYSTEM_PROMPT rule 9 "환각 금지", (2) 테스트 채점기 `hallucinated` 속성으로 자동 FAIL 처리 | 사후 탐지로 충분. 생성 자체를 막을 방법 없음 — 모델 한계. |
| `get_device_alarms` 결과 `[]` (빈 리스트) 일 때 LLM 이 가짜 `alarm_id=1001` / `"Power Supply Failure"` / 학습데이터 추정 시각(2024-05-15) 생성 (2026-05-22 batch Q5 회귀) | rule 9 외에 별도 rule 9-A 추가: `structured_content.result == []` 면 "조회 결과 없음"만 출력하고 example/1001 금지 명시 | **효과 없음 — 추가한 9-A 는 2026-05-22 원복**. rule 9 와 `hallucinated` 사후 탐지에 의존. 같은 결과형(빈 리스트)에서 alarm/device/policy 어느 도구든 재발 가능. **신규 프롬프트/코드 보강 금지.** |
