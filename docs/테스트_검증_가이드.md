# 테스트 검증 가이드

## 0. TDD 개발 순서 (필수)

**구현 전에 테스트를 먼저 작성한다.**

```
1. 테스트 작성 (Red)
   - 구현 없이 테스트 케이스 5개 이상 작성
   - pytest 실행 → 전부 실패 확인

2. 최소 구현 (Green)
   - 테스트를 통과시키는 최소한의 코드만 작성
   - pytest 실행 → 전부 통과 확인

3. 정리 (Refactor)
   - 중복 제거, 가독성 개선
   - pytest 재실행 → 통과 유지 확인
```

**신규 tool 추가 시 순서:**

```
[ ] 1. tests/test_<module>_tools.py 에 TestXxx 클래스 + 5개 케이스 작성
[ ] 2. ! uv run pytest tests/ -k "TestXxx" -v  → 실패(Red) 확인
[ ] 3. tools.py / queries.py / models.py 구현
[ ] 4. ! uv run pytest tests/ -k "TestXxx" -v  → 통과(Green) 확인
[ ] 5. server.py 에 @mcp.tool 등록
[ ] 6. ! uv run pytest tests/ -v               → 전체 회귀 확인
```

## 1. 코드 작성 시 항상 포함할 것

### 구현 함수 + 단위 테스트

신규 함수마다 최소 5개 케이스:

| 유형 | 케이스 예시 |
|------|------------|
| 정상 1 | 기본 입력 → 정상 응답 |
| 정상 2 | 선택 파라미터 포함 → 정상 응답 |
| 엣지 1 | limit 최대 초과 → clamp 적용 확인 |
| 엣지 2 | 빈 결과 → 빈 리스트 / None 반환 |
| 실패 1 | DB 예외 → 예외 전파 확인 |

### 로깅 (Python — `logger.*`)

```python
# console.log 대신 logger 사용
logger.debug("tool=get_device_info device_id=%s", device_id)  # 진입
logger.info("tool=get_device_info elapsed_ms=%d rows=%d", elapsed, count)  # 종료
logger.warning("조건 미충족: %s", reason)                       # 예외 분기
logger.exception("DB 오류")                                     # 예외 발생
```

- `log_tool_call` 컨텍스트 매니저 안에서만 로깅
- `result_count` 는 반드시 `meta["result_count"] = ...` 로 기록

### 가정(assumption) 명시

```python
# [ASSUMPTION] zone_id가 NULL인 장비 입력 시 빈 결과 반환 (에러 아님)
# [ASSUMPTION] device_ids 50개 초과 시 앞 50개만 처리 — 호출자에게 조용히 잘라냄
```

## 2. 테스트 파일 구조

```
tests/
├── test_maria_mcp_tools.py          # 단위 테스트 — DB mock, 빠름 (0.1s 이내)
├── test_maria_mcp_integration.py    # 통합 테스트 — 실 DB 접속 필요
├── test_maria_mcp_rca_integration.py
└── test_maria_mcp_middleware.py     # 미들웨어 단위 테스트
```

**네이밍 규칙**

- 파일: `test_<모듈명>_<종류>.py`
- 클래스: `Test<FunctionName>` (camelCase)
- 함수: `test_<시나리오>` (snake_case)

```python
class TestGetDeviceInfo:
    async def test_success(self): ...
    async def test_empty_result_returns_none(self): ...
    async def test_db_error_propagates(self): ...
```

## 3. Mock 원칙

**단위 테스트: DB는 항상 AsyncMock**

```python
@pytest.fixture
def mock_fetch_one(self):
    with patch("src.maria_mcp.db.fetch_one", new_callable=AsyncMock) as m:
        yield m

# 정상 케이스
mock_fetch_one.return_value = {"device_id": 1, ...}

# 빈 결과
mock_fetch_one.return_value = None

# DB 실패
mock_fetch_one.side_effect = RuntimeError("DB connection failed")
```

**통합 테스트: 실 DB만 허용**

- `test_*_integration.py` 파일에서만 실 DB 접속
- 환경변수 `MARIA_HOST` 없으면 자동 skip:
  ```python
  pytestmark = pytest.mark.skipif(
      not os.getenv("MARIA_HOST"), reason="실 DB 환경 없음"
  )
  ```

## 4. 테스트 실행 방법

> **바이브 코딩 시**: Claude가 실행한 결과는 UI에서 잘릴 수 있어 신뢰하기 어렵다.
> `!` 프리픽스로 직접 실행해서 확인할 것.

### 기본 실행

```bash
# 전체
! uv run pytest tests/ -v

# 단위 테스트만 (빠름)
! uv run pytest tests/test_maria_mcp_tools.py -v

# 통합 테스트만 (실 DB 필요)
! uv run pytest tests/test_maria_mcp_integration.py -v
```

### 커버리지 확인

```bash
! uv run pytest tests/test_maria_mcp_tools.py --cov=src/maria_mcp --cov-report=term-missing -q
```

`MISS` 컬럼에 나오는 라인 번호 = 테스트되지 않은 코드.

### 특정 테스트만 실행

```bash
# 키워드 필터
! uv run pytest tests/ -k "get_device_info" -v

# 클래스 단위
! uv run pytest tests/test_maria_mcp_tools.py::TestGetDeviceInfo -v
```

## 7. 자주 쓰는 검증 패턴

### clamp 검증

```python
async def test_limit_clamped_to_max(self, mock_fetch_all):
    mock_fetch_all.return_value = []
    await tools.get_active_alarms(data_center_id=1, limit=9999)
    _, _, params = mock_fetch_all.call_args[0]
    assert params[-1] == 100  # limit 최대값
```

### 파라미터 순서 검증 (IN 쿼리)

```python
async def test_params_structure(self, mock_fetch_all):
    mock_fetch_all.return_value = []
    await tools.get_active_alarms_for_devices(1, [10, 20], limit=5)
    _, _, params = mock_fetch_all.call_args[0]
    assert params[0] == 1       # data_center_id 첫째
    assert params[-1] == 5      # limit 마지막
    assert 10 in params and 20 in params
```

### 조기 반환 (DB 미호출) 검증

```python
async def test_empty_input_skips_db(self, mock_fetch_all):
    result = await tools.get_active_alarms_for_devices(1, [])
    assert result == []
    mock_fetch_all.assert_not_called()  # DB 쿼리 없었음을 확인
```
